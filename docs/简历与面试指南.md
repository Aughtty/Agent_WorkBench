# 简历与面试指南

## 一、可直接使用的简历项目

### 个人信息工作台 Agent

**项目简介：** 基于 Python 开发单 Agent 多工具个人工作台，接入大模型原生 Function Calling，自主选择知识库检索、本地文件搜索和待办管理工具，支持多轮短期 Memory、来源引用和完整执行 Trace。

**技术栈：** Python、LLM API、Function Calling、RAG、BGE Embedding、BM25、Hybrid Search、FastAPI、SQLite、Streamlit、pytest

**核心工作：**

- 不依赖 Agent 框架实现 Tool Calling 主循环与 Tool Registry，完成模型决策、JSON Schema 参数校验、工具执行、Observation 回传、多步调度、异常回传和最大步骤保护。
- 构建 TXT/Markdown/PDF/DOCX 文档解析、Chunk、BGE 中文 Embedding、BM25 与加权 RRF 混合检索链路，返回可追溯 Chunk 引用；使用 20 条固定问题集对比检索方案。
- 使用 SQLite 持久化知识 Chunk、待办和按 session 隔离的短期对话，通过消息窗口与字符预算控制上下文长度；JSONL Trace 记录模型/工具耗时和执行结果。
- 使用 FastAPI 提供聊天、文档上传和知识库管理接口，使用 Streamlit 提供演示页面；17 项自动测试通过，并建立 8 条真实 Agent 回归案例检查工具选择、引用和执行效率。

## 二、数据应该怎样写

可以写：

- `17 项自动测试通过`。
- `20 条固定检索问题上 Hybrid Hit@3=1.0、MRR@3=0.9417`。
- `建立 8 条真实 Agent 回归案例；最新严格评测通过 7 条，1 条因重复检索超过效率阈值失败`。

必须同时说明数据集较小。不能把 20 条自建问题包装成行业 Benchmark，也不能写“准确率达到 100%”而不解释指标。

## 三、能写、谨慎写、不能写

### 可以写

- 自定义 Agent Tool Calling 主循环。
- 原生 Function Calling 多工具调用。
- BGE Embedding、BM25 和 Hybrid Search。
- SQLite 短期 Memory、FastAPI、Trace、pytest。
- 固定问题集上的实际指标。

### 可以写但要谨慎

- “语义检索”：BGE 是预训练模型，项目负责调用、索引和评测，没有训练模型。
- “向量存储”：当前是进程内向量矩阵 + SQLite Chunk，不是独立 Vector Database。
- “Memory”：只能称短期窗口 Memory，不能称长期记忆。
- “Agent 评测”：是自建小型回归集，不是通用 Agent Benchmark。

### 不应该写

- 自主训练 Embedding 或大模型。
- 自主研发向量数据库。
- 生产级、高并发、高可用。
- 显著降低幻觉、显著提升准确率。
- Multi-Agent、GraphRAG、MCP、微调。

## 四、30 秒项目介绍

我做了一个个人信息工作台 Agent，用来统一处理知识库问答、文件查找和待办管理。核心不是套用 Agent 框架，而是自己实现了模型决策、Tool Calling、工具执行和 Observation 回传循环。RAG 部分支持多种文档解析、BGE Embedding、BM25 和混合检索，并返回 Chunk 来源。项目还包含 SQLite 短期 Memory、FastAPI、Trace 和自动评测，目前 17 项测试通过，并实际验证了 8 类模型工具选择任务。

## 五、1 分钟项目介绍

这个项目来源于我日常管理学习资料、文件和待办的需求。用户只需要用自然语言描述目标，Agent 会根据 JSON Schema 选择知识检索、文件搜索或待办工具，并根据工具结果继续执行。为了真正理解底层协议，我没有直接使用 LangChain 的一行式 Agent，而是实现了 Tool Registry、call_id 关联、Observation 回传、错误处理和最大步骤保护。知识库支持 TXT、Markdown、PDF、DOCX，使用 BGE 中文 Embedding、BM25 和加权 RRF 混合检索，回答保留具体 Chunk 引用。工程上使用 SQLite 管理 Chunk、待办和会话，FastAPI 提供接口，Streamlit 用于演示。测试分为 pytest、20 条检索集和 8 条真实 Agent 案例，结果与限制都记录在仓库中。

## 六、3 分钟项目介绍

我做这个项目是因为个人资料、项目文件和待办分散在不同位置，普通 ChatBot 只能生成文本，不能可靠地读取和修改本地状态。因此我设计了一个单 Agent 多工具工作台。

请求进入后，Agent 先读取当前 session 的最近消息，再把消息和所有工具的 JSON Schema 发给学校大模型。模型如果返回 tool_calls，应用会校验工具名和参数、执行真实 Python 函数，再把结果作为 role=tool 的 Observation 回传。模型可以继续调用其他工具，或者输出最终答案。为了防止失控，我加入了未知工具拒绝、完整 Schema 校验、工具异常回传、429/5xx 重试和最大步骤限制。

RAG 部分将文档解析后按段落和字符长度切 Chunk，保留 source 和 position。检索同时使用 BM25 与 BGE-small-zh-v1.5 的 512 维向量，再使用加权 RRF 融合排名。最初等权 Hybrid 在一条“智能体无限循环”问题上漏掉了正确文档，因此我通过固定评测集发现问题，将 BM25/向量权重调整为 1.4/1.0，重新得到 Hit@3=1.0。这个实验也说明 Embedding 不会自动优于词法检索。

工程上使用 SQLite 保存 Chunk、待办和按 session 隔离的短期 Memory，FastAPI 提供聊天和文档上传接口，Streamlit 用于演示，JSONL Trace 记录每一步工具参数、结果和耗时。当前有 17 项自动测试、20 条检索评测和 8 条真实 Agent 评测。项目局限是数据集仍小、向量索引在进程内、没有 Reranker 和多用户鉴权，所以我不会把它描述成生产级系统。

## 七、五层面试题与参考回答

### 第一层：项目基础

**1. 为什么需要 Agent，而不是普通 ChatBot？**

一句话：普通 ChatBot 只能生成回答，我的场景还需要根据目标读取知识、查询文件或修改待办。项目中模型动态选择工具并根据 Observation 决定下一步；如果流程完全固定，我会优先使用 Workflow。

**2. 为什么是单 Agent 而不是 Multi-Agent？**

当前任务共享同一个用户目标和工具集，不存在明确的角色隔离需求。Multi-Agent 会增加消息传递、状态同步、延时和评测难度，因此第一版用单 Agent 多工具更容易稳定和解释。

### 第二层：Agent

**3. Tool Calling 的完整过程是什么？**

模型读取 Tool Schema，生成工具名和 JSON 参数；应用解析并校验参数，执行 handler，把结果用同一个 call_id 作为 role=tool 消息回传；模型再决定继续或回答。模型不直接执行 Python。

**4. 为什么 `ModelClient` 使用 Protocol？**

让 `Agent` 依赖统一的 `complete()` 能力，而不是学校 API 的原始响应格式。换模型服务或在测试中使用 Fake Model 时，Agent 主循环无需修改。

**5. 工具调用失败怎么办？**

工具异常被包装成 `ok=false` Observation。模型可根据错误决定修正参数或说明失败；未知工具不会执行。模型网络瞬时错误和 429/5xx 才重试，鉴权和参数错误不盲目重试。

**6. 为什么需要最大步骤？**

模型可能重复调用工具。最大步骤同时是死循环、延时和 Token 成本的硬边界。项目默认 6 步。

### 第三层：RAG

**7. 为什么 Chunk 是 500/80？**

这是适合当前中文笔记的初始值：500 字能保留一个完整小节，80 字重叠降低边界信息丢失。它不是全局最优，需要在更多真实文档上比较 Hit@K、回答质量和 Token 成本。

**8. 为什么同时用 BM25 和 BGE？**

BM25 擅长专有名词和精确关键词，BGE 擅长不同措辞。项目使用 RRF 融合排名，不直接相加不同量纲的分数。

**9. 为什么 BM25 权重是 1.4？**

等权 Hybrid 在 20 条小型评测中漏了一条 Hit@3；当前文档术语明确，BM25 更稳定。调到 1.4/1.0 后 Hit@3 恢复到 1.0。这只是在当前回归集上的经验参数。

**10. 当前是否用了向量数据库？**

没有独立 Vector Database。SQLite 保存 Chunk，向量矩阵在进程内重建。可以称本地 Vector Store；数据扩大后迁移 Qdrant、Milvus 或 pgvector。

### 第四层：工程

**11. Memory 如何防止串线？**

每条消息带 `session_id`，查询历史时使用同一个 session 过滤，并有自动测试验证两个 session 隔离。真实多用户系统还要把 session 与鉴权 user_id 绑定。

**12. 如何控制上下文成本？**

当前同时限制最近 12 条消息和 12000 字符；RAG 只返回 Top-K Chunk。进一步可以用 Tokenizer 精确预算和历史摘要。

**13. Trace 记录什么？**

记录输入、步骤、模型/工具耗时、工具名、参数、结果、模型、usage 和最终回答，不记录 API Key。它用于 Debug、评测和成本分析。

**14. 为什么测试不都调用真实模型？**

真实模型有费用、网络波动和非确定性。pytest 使用 Fake Model 做稳定回归；少量端到端评测再调用真实服务。

### 第五层：代码追问

**15. `agent.py` 为什么先追加 assistant tool_calls，再追加 tool result？**

Chat Completions 协议要求保留模型发出的 Tool Call，随后用相同 call_id 返回结果。只发 tool result 会丢失关联上下文。

**16. `tools.py` 为什么用 Registry，而不是在 Agent 中写 if/elif？**

Registry 把工具发现、Schema 和执行统一起来，新增工具不需要修改 Agent 主循环，也更容易拒绝未知工具和单独测试。

**17. 新文档为什么要重建向量矩阵？**

当前数据量小，重建实现简单且结果一致；代价是规模增大后入库慢。因此这是 MVP 取舍，不适合百万 Chunk。

**18. 为什么 Agent 评测规则改过？**

第一版只检查预期工具是否出现，把额外幻觉的 `answer` 工具和过短回答误判为成功。后来增加额外工具、回答完整性、引用和效率检查；不同运行出现 8/8 与 7/8，暴露了模型重复检索的非确定性。

## 八、项目亮点

真正的亮点不是库的数量，而是：核心 Agent 循环可解释；真实模型多工具调用已验证；RAG 有词法/神经/混合基线和失败案例；有 API、Trace、测试和明确边界；能区分自己、框架和服务做了什么。
