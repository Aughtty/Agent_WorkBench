## 2. 从样本归纳出的能力频率

这不是严格统计学结论，而是基于上述 7 个定向样本的求职决策归纳。

| 能力 | 频率判断 | 半个月策略 |
|---|---:|---|
| Python / 扎实编程 | 极高 | 必须用项目代码与测试证明 |
| Agent / Tool Calling / Function Calling | 极高 | 必须自己解释主循环和 Schema |
| RAG / 检索 / Embedding | 极高 | 必须做完整可测链路 |
| Prompt / 结构化输出 | 高 | 必须有模板、失败样例和迭代记录 |
| 后端 API（FastAPI/Spring） | 高 | Python 路线补 FastAPI |
| 上下文 / Memory | 中高 | 做短期会话窗口即可，不扩张长期记忆 |
| 日志、Trace、测试、评测 | 中高 | 是区分“Demo”和工程项目的关键 |
| LangChain/LangGraph 等框架 | 中高，多为优先/加分 | 先懂底层循环，再用 LangGraph 对照重构一小段 |
| MCP / Skill | 中等偏上、上升明显 | 第二阶段理解并做 1 个薄适配，不作为 MVP 核心 |
| Docker / 部署 | 中等，多为加分 | 项目稳定后补 Docker，不抢占前 7 天 |
| 微调/RLHF/训练/分布式推理 | 部分算法岗高频 | 本轮不主攻；与你的 PyTorch 背景形成认知补充即可 |
| Multi-Agent / GraphRAG / Kubernetes | 非入门交集 | 暂缓 |

## 3. 你的能力差距

### 已有基础，可直接迁移

- Python、PyTorch、深度学习基本概念。
- 阅读论文和复现代码的能力。
- Linux、Conda、服务器环境和基础 Debug。
- 研究生训练带来的问题拆解和实验意识。

### 半个月内必须补齐

- LLM API 与原生 Tool Calling 完整消息协议。
- Agent 的决策—行动—观察循环、失败恢复和循环保护。
- RAG 的文档处理、Chunk、Embedding、Retrieval、Top-K、来源引用与评测。
- FastAPI、SQLite、配置、异常、日志、自动测试。
- 能用自己的代码解释“我写的 / 框架做的 / 模型服务提供的”。

### 只建立概念、不投入大量开发

- LangGraph 状态图与 MCP 协议：理解价值，做最小对照或适配。
- Docker：完成本地功能后再容器化。
- Rerank、混合检索、可观测平台：有基线评测后再加。

### 暂不学习

- 预训练、复杂 RLHF、分布式训练、vLLM 性能优化。
- Multi-Agent、GraphRAG、Kubernetes、复杂前端。

原因不是这些技术不重要，而是它们无法在 14 天内最大化第一段应用开发实习的投递能力。

## 4. 三个候选项目横向比较

评分为 1～5，越高越有利；开发风险一列越高表示风险越大。

| 候选项目 | 日常用途 | Agent 必要性 | 岗位匹配 | 半月完成 | 稳定/可测 | 演示与面试 | 开发风险 |
|---|---|---:|---:|---:|---:|---:|---:|
| A. 个人信息工作台 Agent | 知识、文件、待办统一入口 | 多类目标需动态选工具并连续执行 | 5 | 5 | 5 | 5 | 2 |
| B. 招聘 JD 分析与投递助手 | 收集 JD、对比技能、跟踪投递 | 搜索、抽取、对比、数据库需组合 | 5 | 4 | 4 | 5 | 3 |
| C. 网页研究与学习简报 Agent | 多网页收集、证据整理、输出简报 | 规划搜索、去重、引用、多轮补查 | 4 | 3 | 3 | 5 | 4 |

### A. 个人信息工作台 Agent

- 核心：知识库问答、本地文件查找、待办管理、会话 Memory、执行 Trace。
- 为什么需要 Agent：同一句目标可以同时触发检索与写入；执行顺序不能完全写死。
- 技术：Tool Schema、Tool Calling 主循环、RAG、SQLite、Memory、API、日志、测试。
- 最大风险：功能容易摊大；通过只保留 3 类工具控制范围。
- 面试价值：能覆盖多数 JD 交集，且每个模块能现场演示和单元测试。

### B. 招聘 JD 分析与投递助手

- 核心：导入 JD、结构化抽取、技能聚类、简历匹配、投递状态。
- 为什么需要 Agent：根据任务选择网页/文档解析、数据库查询、比较和生成工具。
- 优点：与你当前求职高度相关，故事自然。
- 风险：网页反爬、招聘页面失效和数据合规会吞噬时间；容易把精力花在采集而非 Agent。
- 半月取舍：可在 A 完成后，把“JD 文档分析”作为知识库真实案例，而不单独建项目。

### C. 网页研究与学习简报 Agent

- 核心：围绕主题搜索多个来源、抽取证据、去重、形成带引用简报。
- 为什么需要 Agent：搜索结果不充分时需要继续检索或改变查询。
- 优点：Agent 决策感最强，演示直观。
- 风险：依赖搜索 API、页面解析和网络稳定性；评测“答案好坏”比本地工具更难。
- 半月取舍：暂不作为主项目；后续可增加一个受控 Web Search Tool。

## 5. 最终选择

选择 **A：个人信息工作台 Agent**。

决策依据不是技术最多，而是：

```text
完成度 × 岗位匹配度 × 稳定性 × 可解释性
```

它既能证明 Agent 确实在做工具选择，又可以把网络、复杂部署和多 Agent 排除在 MVP 之外。B 的求职场景可作为 A 的一组真实知识库文档与演示案例，C 的 Web Search 可在核心功能稳定后作为可选增强。

## 6. 分阶段范围

### MVP（当前 0.1）

- 自己实现 Agent Tool Calling 循环。
- 知识检索、文件查找、待办 3 类工具。
- SQLite Memory、Trace、失败回传、循环保护。
- 离线可重复演示和自动测试。

### 第二阶段（达到可投递版本的核心）

- 真实 OpenAI-compatible LLM Tool Calling。
- 文档导入、Chunk、Embedding、向量索引、来源引用。
- FastAPI、超时/重试、配置校验。
- 至少 20 条固定评测集：工具选择、参数、检索命中、最终答案。

### 最终版（时间允许再做）

- 简单 Streamlit UI。
- Hybrid Search 或 Rerank 的对比实验。
- Docker 与演示部署。
- 一个 MCP Tool 适配，用于展示协议理解；不扩张成 MCP 平台。
