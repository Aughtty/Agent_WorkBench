# 项目学习指南

这份文档按“整体 → 模块 → 文件 → 核心代码 → 数据流 → 实例”学习。你不需要重新编写项目，但必须能沿真实代码解释一次请求。

## 1. 知识体系

```text
LLM 应用开发
├── Prompt：告诉模型角色、目标和约束
├── RAG：给模型补充外部且可追溯的知识
├── Agent：让模型在运行时选择行动
│   ├── Tool Schema
│   ├── Tool Calling
│   ├── Observation
│   ├── Memory
│   └── Stop Condition
├── Workflow：由开发者预先确定主要步骤
└── Fine-tuning：训练模型参数（本项目不使用）
```

本项目是单 Agent 多工具应用，RAG 是 Agent 可以调用的一项工具能力。

## 2. 一次完整请求

```text
用户问题
  ↓
Agent 读取 session_id 对应的最近 Memory
  ↓
LLM 读取 messages + Tool Schema
  ↓
LLM 返回 tool_calls 或最终文本
  ↓ tool_calls
ToolRegistry 使用 JSON Schema 校验参数
  ↓
执行 RAG / 文件 / SQLite Todo
  ↓
结果作为 role=tool Observation 回传
  ↓
LLM 再次判断
  ↓
最终回答写入 Memory，完整过程写入 Trace
```

真实案例“查 Top-K 并新增待办”使用 3 次模型调用、2 次工具调用。`steps` 统计模型轮次，不是工具数量。

## 3. Agent 与 Tool Calling

### 代码位置

- `contracts.py`：统一的 `ToolCall`、`ModelTurn`、`ModelClient`。
- `tools.py`：`Tool`、`ToolRegistry` 和 5 个业务工具。
- `llm_client.py`：学校 API 请求与原生 `tool_calls` 解析。
- `agent.py`：主循环。

### Tool 的四部分

```python
Tool(
    name="add_todo",
    description="新增一条待办事项。",
    parameters={...JSON Schema...},
    handler=todos.add,
)
```

- `name/description/parameters` 发给模型。
- `handler` 只由 Python 应用持有。
- 模型生成调用请求，不能直接执行 `todos.add()`。

### 主循环

`Agent.run()` 每轮调用 `model.complete(messages, schemas)`。有 Tool Call 就执行并追加 Observation；没有 Tool Call 就把 `content` 当作最终答案。`max_steps` 防止模型无限循环。

### 失败处理

- 未知工具：返回 `ok=false` Observation，不执行任意函数。
- 参数错误：`Draft202012Validator` 检查类型、范围、枚举和额外字段。
- 工具异常：捕获后回传错误类型，Agent 不直接崩溃。
- 模型 HTTP 429/5xx/网络错误：指数退避重试。
- 401/403/400：不可恢复，不盲目重试。

### 面试回答

一句话：Tool Calling 是模型根据 Schema 生成结构化调用请求，应用负责校验和执行，再把结果作为 Observation 回传给模型。

继续追问时结合 `agent.py` 的循环、`tools.py` 的 Registry 和 `llm_client.py` 的 JSON 解析说明。

## 4. RAG

### 代码位置

全部核心逻辑位于 `rag.py`：

- `DocumentLoader`：TXT/MD/PDF/DOCX → 文本。
- `TextChunker`：段落优先切块，超长段字符兜底，保留 Overlap。
- `SQLiteChunkStore`：持久化 Chunk 与元数据。
- `BM25Retriever`：词法相关性基线。
- `LocalVectorRetriever`：字符 n-gram TF-IDF 向量基线。
- `FastEmbedRetriever`：BGE 512 维神经 Embedding。
- `HybridKnowledgeBase`：入库、检索和加权 RRF。

### 完整数据流

```text
文档
→ 解析纯文本
→ chunk_size=500 / overlap=80
→ SQLite 保存 source、position、text
→ BGE 生成 512 维向量
→ Query 生成向量
→ 余弦相似度排名
→ BM25 排名
→ Weighted Reciprocal Rank Fusion
→ Top-K Chunk + citation
→ Agent 把结果交给 LLM 生成答案
```

### 为什么混合检索

BM25 对专有名词和精确关键词强；BGE 能处理不同措辞。两种分数不在同一量纲，所以项目没有直接相加，而是用 RRF 融合名次。小型评测发现等权融合曾漏掉 1 条 Hit@3，因此最终给 BM25 权重 1.4、向量权重 1.0。这个权重只对当前小数据集负责。

### Chunk 取舍

- 太小：上下文断裂、索引数量增加。
- 太大：无关内容增加、定位变差、Token 上升。
- Overlap 太小：边界信息丢失。
- Overlap 太大：重复召回。

当前 500/80 是可解释初始值，不是假装成全局最优。

### Vector Store 与 Vector Database

项目使用 SQLite 保存 Chunk，进程内保存向量矩阵。它是本地 Vector Store，不是独立 Vector Database。数据规模扩大后应迁移 Qdrant、Milvus 或 pgvector。面试中不能说“自主实现向量数据库”。

## 5. Memory

### 代码位置

`memory.py` 的 `MemoryStore`。

### 当前策略

- SQLite 持久化消息。
- `session_id` 隔离不同会话。
- 最多读取最近 12 条消息。
- 同时设置 12000 字符预算。

数据库只是存储；最近窗口和字符预算才是 Memory 策略。当前没有长期用户画像、摘要或相关记忆检索，不能写“长期记忆”。

## 6. FastAPI 与 UI

`api.py` 提供：

- `GET /health`
- `POST /chat`
- `POST /documents/text`
- `POST /documents/upload`
- `GET /documents`
- `DELETE /memory/{session_id}`

接口层负责长度、文件类型、10 MB 大小限制和 HTTP 错误映射。业务逻辑不写在路由中，而是调用 `AppComponents`。

`ui.py` 只负责展示、上传和调用核心服务。UI 删除后，Agent/RAG/API 仍可运行。

## 7. Trace 与评测

`agent.py` 把 JSONL 写到 `logs/agent.jsonl`，字段包含：会话、输入、模型轮次、工具名、参数、结果、模型耗时、工具耗时、模型名、usage 和最终回答。API Key 从不写入 Trace。

测试分三层：

1. pytest：Fake Model，不调用真实服务，保证确定性。
2. 检索评测：20 条固定 query/source，计算 Hit@3 和 MRR@3。
3. Agent 评测：8 条真实模型案例，检查预期工具、额外工具、回答长度、引用和步骤效率。

原 Agent 评测曾把“出现预期工具但额外幻觉 answer 工具”误判为成功。收紧标准并修改 Prompt 后重新获得 8/8。这说明评测规则本身也必须审查。

## 8. 自己、框架、服务分别做了什么

### 自己实现

- Agent 主循环、停止条件、Trace。
- Tool Registry、Schema 组织、错误回传。
- 文档 Chunk、BM25、加权 RRF、引用格式。
- SQLite Chunk/Todo/Memory。
- API 业务边界、评测数据和脚本。

### 库实现

- FastEmbed/ONNX：加载并运行 BGE。
- scikit-learn：TF-IDF 和余弦相似度。
- pypdf/python-docx：文档解析。
- jsonschema：完整参数验证。
- FastAPI/Streamlit：服务和界面基础设施。

### 第三方服务

- `tju-llm`：理解用户目标、选择工具、生成工具参数和最终语言回答。
- BGE 模型权重：预训练语义表示；项目没有自行训练 Embedding。
