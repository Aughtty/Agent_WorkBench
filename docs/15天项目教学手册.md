# 个人信息工作台 Agent：15 天源码主线教学教程

> 目标：读懂、修改并能面试讲解真实 Agent 项目。每天 1～3 小时；你先阅读、运行和复述，不需要先修改代码。

## 0. 使用方法

这不是“文件名＋一句用途”的说明书。每天都按以下顺序学习：

1. 指出今天处于主调用链哪一步；
2. 把理论映射到真实文件、类、函数和关键语句；
3. 说明输入、内部步骤、输出、调用者和被调用者；
4. 解释设计原因，而不只是翻译语法；
5. 用代码阅读题、理解题和导师/面试题验收。

代码位置以当前项目为准。优先搜索类名或函数名，不依赖容易变化的绝对行号。每天完成后发送：

```text
Day N 已完成
实际学习时间：
我能独立讲出的调用链：
最不理解的代码位置：
代码阅读题答案：
面试题口述答案：
运行结果或报错：
```

## 2. 全项目主调用链

### 2.1 在线 CLI 主链

```text
用户输入
  ↓ main.py::main()
build_online_app(data_dir)
  ↓ app.py::build_components(data_dir, online=True)
创建 KnowledgeBase / ToolRegistry / MemoryStore / OpenAICompatibleClient
  ↓ 注入 Agent(...)
Agent.run(user_input, session_id)
  ↓ memory.recent() + SYSTEM_PROMPT + 当前 user message
messages: list[dict]
  ↓ registry.schemas()
tools: list[JSON Schema]
  ↓ model.complete(messages, tools)
llm_client.py 构造 HTTP JSON → 学校 Chat Completions API
  ↓
ModelTurn(content, tool_calls, usage, model)
  ├─ tool_calls 为空 → 保存 assistant memory → 返回 AgentResult
  └─ 有 tool_calls
       ↓ registry.execute(name, arguments)
       JSON Schema 校验 → handler(**arguments)
       ↓ result: {ok, data/error}
       ↓ tool_result_message(call_id, result)
       role=tool Observation 追加到 messages
       ↓ 回到 model.complete(...)
最终答案 → Memory + Trace(JSONL) → CLI 打印
```

### 2.2 API 和 UI 只是换入口

```text
POST /chat → api.py::chat() ─────┐
Streamlit chat_input → ui.py     ├→ service.agent.run(...) → 同一条主链
CLI input() → main.py            ┘
```

三种入口没有三套 Agent，这叫业务核心与表现层分离。

### 2.3 一轮工具调用的数据变化

```text
"查 Tool Calling"                         # str
  ↓
{"role":"user","content":"..."}          # message dict
  ↓ LLM 原始 response JSON
choices[0].message.tool_calls[*]
  ↓ llm_client.py 解析
ToolCall(name, arguments: dict, call_id)   # 内部对象
  ↓ ToolRegistry 执行
{"ok":true,"data":{...}}                 # 工具结果 dict
  ↓ tool_result_message()
{"role":"tool","tool_call_id":...,      # Observation message
 "content":"{...JSON字符串...}"}
  ↓ 再次请求 LLM
ModelTurn(content="综合答案", tool_calls=[])
  ↓
AgentResult(answer, steps, trace)
```

# Day 1：从入口到答案——先跑通整条链

## 今天在主链的位置

沿 `main.py → app.py → Agent.run()` 建立地图，暂不钻算法。

## 理论 ↔ 代码

| 概念 | 理论上 | 本项目中 |
|---|---|---|
| Entry Point | 接收外部输入 | `main.py::main()`、`api_main.py`、`ui.py` |
| Dependency Injection | 外部创建依赖后传给对象 | `app.py::build_components()` → `Agent(...)` |
| Agent | 围绕目标反复决策、行动、观察 | `agent.py::Agent.run()` |
| State | 本轮决策所需信息 | `messages`、`trace`、`step` |

## 对应代码

- 文件：`main.py`
- 函数：`main()`
- 关键位置：参数解析、`build_*_app()`、`agent.run()`
- 下游：`app.py::build_components()`、`agent.py::Agent.run()`

### 文件级：`main.py`

职责：把终端输入转换为业务调用。它不应知道 HTTP payload、SQLite 表或 BM25。

删除影响：CLI 不能启动；API/UI 仍可运行。删除 `agent.py` 则三种入口都失去核心能力。

```python
agent = build_online_app(Path(args.data_dir)) if args.online else build_offline_app(Path(args.data_dir))
result = agent.run(question, session_id="cli")
print(f"助手：{result.answer}")
```

执行过程：

1. `args.data_dir` 是命令行字符串，`Path` 将其转为路径对象；
2. `--online` 只决定注入真实模型还是替身，不改变主循环；
3. `build_*_app()` 返回 `Agent`；
4. `question` 是 `input()` 得到的字符串；
5. `session_id="cli"` 让 CLI 历史与 API/UI 隔离；
6. `run()` 返回 `AgentResult`，入口可读取 `answer/steps/trace`；
7. CLI 只打印 answer，API/UI 还能展示 trace。

### 文件级：`app.py`

它是组装层（composition root）：

```text
build_components()
├── SQLiteChunkStore + TextChunker → HybridKnowledgeBase
├── create_registry(..., knowledge) → ToolRegistry
├── MemoryStore → memory
├── online ? OpenAICompatibleClient : OfflineDemoModel → model
└── Agent(model, registry, memory, log_path) → agent
```

```python
agent = Agent(model=model, registry=registry, memory=memory,
              log_path=Path("logs") / "agent.jsonl")
```

为什么不让 `Agent` 自己创建这些对象：否则它会与厂商、磁盘路径和工具集绑死，测试无法传入 `ScriptedModel`，离线模式也要修改 Agent 源码。这是依赖注入。

## 数据流

```text
input() -> str
Path(data_dir) -> 配置输入
build_online_app() -> Agent
Agent.run(str, "cli") -> AgentResult
AgentResult.answer -> print()
```

## 阅读任务与验收

1. 从 `if __name__ == "__main__"` 反向找到 `main()`；
2. 找出 demo、online、默认离线三条分支；
3. 为 `build_components()` 每个局部变量写出实际类型；
4. 运行 `python main.py --demo`；
5. 不看文档画出主链，解释为什么入口不实现 Agent。

## 提问

- 代码阅读：`main.py` 是否直接调用学校 API？`result` 为什么不是字符串？
- 理解：删除 `ui.py` 和删除 `agent.py` 的影响为何不同？
- 面试：“程序从哪里启动，一次请求怎样走？”
  - 初级：`main.py → Agent.run() → LLM/Tool → answer`；
  - 较好：补充依赖组装、messages/schema、Observation 和停止条件；
  - 代码追问：指向 `main()`、`build_components()`、`Agent.run()`。

# Day 2：数据契约与依赖组装——模块凭什么能互换

## 今天在主链的位置

位于对象创建注入阶段，以及 LLM 原始 JSON 进入 Agent 前的统一格式阶段。

## 对应代码

- `contracts.py::ToolCall`：一次结构化工具请求；
- `contracts.py::ModelTurn`：一轮模型输出；
- `contracts.py::ModelClient`：模型适配器协议；
- `agent.py::AgentResult`：整个任务输出；
- `app.py::build_components()`：实际类型的选择和注入。

### 文件级：`contracts.py`

学校 API 返回 JSON，离线模型生成 Python 对象，测试模型又是手写替身。此文件定义共同语言。删除后，Agent 会绑定厂商响应格式，换模型和测试都要改主循环。

```text
ToolCall(name, arguments, call_id)
ModelTurn(content, tool_calls, usage, model)
ModelClient.complete(messages, tools) -> ModelTurn
```

### `ToolCall`

```python
@dataclass(frozen=True)
class ToolCall:
    name: str
    arguments: dict[str, Any]
    call_id: str
```

- 来源：`llm_client.complete()` 从 JSON 解析，也可由替身直接构造；
- `name`：给 Registry 查找工具；
- `arguments`：适配器已保证是 dict；
- `call_id`：将结果对应回某次请求；
- `frozen=True`：构造后不应修改，减少状态污染。

### `ModelTurn`

```text
tool_calls=[]              → content 是最终回答
tool_calls=[ToolCall(...)] → 需要 Agent 先执行工具
```

`usage/model` 不参与决策，但进入 Trace 供成本、延迟和版本分析。

### `ModelClient(Protocol)`

它规定任何模型对象只要提供兼容的 `complete()` 就能被 Agent 使用：

- `OpenAICompatibleClient`：真实服务；
- `OfflineDemoModel`：离线演示；
- `ScriptedModel`：测试“工具→回答”；
- `LoopingModel`：测试无限循环保护。

### 关键代码：`Agent.__init__()`

```python
def __init__(self, model: ModelClient, registry: ToolRegistry,
             memory: MemoryStore, log_path: Path, max_steps: int = 6, ...):
    self.model = model
    self.registry = registry
    self.memory = memory
```

`model/registry/memory` 均在 `build_components()` 创建。Registry 内部不是 list，而是 `dict[str, Tool]`。保存为实例属性是因为每次 `run()` 和多轮循环都会使用。新增工具通常只改 `create_registry()`；更换模型只替换 `ModelClient` 实现。

## 阅读任务与提问

1. 为 `build_components()` 每个构造器写输入输出；
2. 比较真实 Client 和 `ScriptedModel.complete()` 的共同契约；
3. 找出 `AgentResult` 在 CLI/API/UI 被读取的字段；
4. 为什么 arguments 不保留 JSON 字符串？
5. `call_id` 和工具名各解决什么问题？

面试：“如何让 Agent 与具体模型解耦？”较好回答应指出 `ModelClient.complete() -> ModelTurn`，原始厂商 JSON 只在适配器解析，Agent 从不读取 `choices[0]`。

# Day 3：LLM 调用——从 messages 到 ModelTurn

## 今天在主链的位置

`Agent.run()` 调 `self.model.complete(messages, schemas)`，HTTP 往返后得到 `ModelTurn`。

## 对应代码

- `config.py::load_env_file()` / `LLMSettings.from_env()`；
- `llm_client.py::OpenAICompatibleClient.complete()` / `_post()`；
- 调用点：`agent.py::run()` 的 `turn = self.model.complete(...)`；
- 测试：`tests/test_llm_client.py::FakeClient`。

### 文件级：`llm_client.py`

上游是内部 Python 数据，下游是学校 HTTP API。它负责格式转换和可靠传输，不执行工具。删除后在线模式失效，离线模式仍可运行。

```text
OpenAICompatibleClient
├── __init__(settings)         保存 URL/Key/模型/超时/重试
├── complete(messages, tools)  payload 与 ModelTurn 转换
└── _post(payload)             HTTP、鉴权、重试、JSON 解码
```

### 关键调用逐项解释

```python
turn = self.model.complete(messages, self.registry.schemas())
```

1. `self.model` 在 `build_components()` 注入，在线为 `OpenAICompatibleClient`；
2. `messages` 由 system、Memory、当前 user 构造，循环中还追加 assistant/tool；
3. 类型为 `list[dict[str, Any]]`；
4. `schemas()` 把 Tool 转成 function schemas；
5. `complete()` 表示一轮模型决策；
6. `turn` 是 `ModelTurn`，不是原始 response dict；
7. 后续通过 `turn.tool_calls` 判断行动还是结束；
8. 这一步就是当前实现中的模型 planning。

第一次请求的 messages：

```python
[
  {"role":"system", "content":"你是个人信息工作台 Agent..."},
  # 可选的历史 user/assistant
  {"role":"user", "content":"查 Tool Calling 并记录待办"}
]
```

工具后会增加 assistant 的 `tool_calls` 请求和带相同 `tool_call_id` 的 role=tool 结果。两者都要保留，模型才能理解 Observation 对应哪次调用。

### `complete()` 内部

```text
messages + tools
→ payload(model/messages/tools/tool_choice=auto)
→ _post()
→ response[choices][0][message]
→ arguments JSON string 经 json.loads 变 dict
→ ToolCall 列表
→ ModelTurn(content/tool_calls/usage/model)
```

只有 tools 非空才发送 `tools` 和 `tool_choice="auto"`，模型可自行选择直接回答或调用工具。

### `_post()` 边界

- dict 序列化为 UTF-8 bytes；Key 只加入 Authorization header；
- 429 和 5xx 重试，普通 4xx 不盲目重试；
- 网络失败最终转成 `LLMRequestError`；
- 退避为 `0.5 * 2**attempt`；
- 响应格式错误转成 `LLMProtocolError`；
- API 层将两类错误映射为 502。

`FakeClient` 重写 `_post()`，从而只测试 payload 构造和解析，不受网络、余额和随机性影响。

## 代码阅读题

```python
arguments = function.get("arguments", "{}")
if isinstance(arguments, str):
    arguments = json.loads(arguments)
```

1. 为什么 arguments 经常是字符串？
2. `json.loads` 后为何还检查 dict？
3. 解析失败为何是 ProtocolError 而不是工具错误？
4. `raw_call.get("id") or f"call-{index}"` 防御什么？

面试：“LLM 调用层做了哪些工程处理？”较好回答应包含协议适配、内部结构化类型、超时、429/5xx 重试、错误分类和 Key 不落日志，并能定位 `complete()` 与 `_post()`。

# Day 4：Tool Calling——Schema、Registry、校验与执行

## 今天在主链的位置

前半是 `registry.schemas()` 告诉模型能力，后半是 `registry.execute()` 执行模型返回的 `ToolCall`。

## 理论 ↔ 代码

| 概念 | 项目位置 | 实际含义 |
|---|---|---|
| Tool Schema | `Tool.schema()` | 给模型看的名字、描述、参数约束 |
| Registry | `ToolRegistry._tools` | 工具名到 Tool 的字典 |
| Tool Selection | `ToolCall.name` | 由模型选择，不是 Python planner |
| Executor | `ToolRegistry.execute()` | 应用校验并调用 handler |
| Observation | `tool_result_message()` | 执行结果变为 role=tool |

### 文件级：`tools.py`

它是能力边界。模型只能请求，不能直接运行 Python、读库或遍历磁盘。删除后模型还可返回文本，但 Agent 没有受控行动能力。

```text
Tool → schema()
ToolRegistry → register() / schemas() / execute()
create_registry()
├── search_knowledge → knowledge.search
├── find_files → files.find
├── add_todo → todos.add
├── list_todos → todos.list
└── complete_todo → todos.complete
tool_result_message()
```

### Registry 为什么用 dict

```python
self._tools: dict[str, Tool] = {}
self._tools[tool.name] = tool
```

同一对象同时带 schema 和 handler：给模型时遍历 `schema()`，执行时用模型返回的 name 查找。新增工具只注册，不改循环；重名立即拒绝。

### 执行语句逐项解释

```python
tool = self._tools.get(name)
errors = sorted(Draft202012Validator(tool.parameters).iter_errors(arguments), ...)
return {"ok": True, "data": tool.handler(**arguments)}
```

1. `name/arguments` 来自 `ToolCall`，最终来自模型；
2. `get()` 形成白名单，不存在时返回结构化错误；
3. 模型输出不可信，要按同一 Schema 再校验；
4. handler 是 `knowledge.search` 等 Python callable；
5. `**arguments` 将 dict 展开为关键字参数；
6. 成功包成 `{ok:true,data:...}`；
7. handler 异常包成 `{ok:false,error:...}`；
8. 失败成为 Observation，而非让 Agent 崩溃。

Schema 同时用于模型生成指导、执行前校验和接口文档。Schema 中 `default` 不会自动填值；省略参数可工作是因为 handler 有 Python 默认值。

```python
result = self.registry.execute(call.name, call.arguments)
messages.append(tool_result_message(call.call_id, result))
```

role=tool 的 content 必须是字符串，因此 `json.dumps()`；`tool_call_id` 必须与请求一致。

## 阅读题与面试题

1. tool_name、arguments 各从哪里来？
2. 为什么不能让模型提供任意 Python 函数名？
3. 工具不存在、参数错误、handler 异常分别怎样返回？
4. 新增 `delete_todo` 修改哪里？为何不用改 Agent？

面试：“Tool Calling 与普通函数调用有什么区别？”较好回答必须串起 `Tool.schema() → LLM → ToolCall → Registry.execute() → tool_result_message()`，并提到白名单、校验、call_id 和 Observation。

# Day 5：Agent 主循环——一次 LLM 调用为什么不够

## 今天在主链的位置

进入核心 `agent.py::Agent.run()`，model、registry、memory 在这里协作。

### 文件级：`agent.py`

它是编排层，不实现检索、SQL 或 HTTP，只组织“上下文→决策→动作→观察→再决策→停止”。删除后组件仍能单独工作，但不再形成 Agent。

```text
AgentResult(answer, steps, trace)
Agent
├── __init__()      持有依赖与步数上限
├── run()           主循环
└── _write_trace()  追加 JSONL
```

### 输入输出

```python
run(user_input: str, session_id="default") -> AgentResult
```

输入是自然语言和会话隔离键；输出含 answer、模型决策轮数 steps、本次 trace；副作用包括 Memory、工具执行和日志。

### 1. 初始状态

```python
messages = [{"role":"system", "content":self.system_prompt},
            *self.memory.recent(session_id)]
user_message = {"role":"user", "content":user_input.strip()}
messages.append(user_message)
self.memory.append(session_id, user_message)
trace = []
```

字符串和 SQLite 历史变为有序 messages。system 每次临时置顶但不重复存库，当前 user 同时持久化。

### 2. 模型决策

```python
for step in range(1, self.max_steps + 1):
    turn = self.model.complete(messages, self.registry.schemas())
```

项目没有 `Planner.plan()`。模型依据 messages 和 schemas 产生 ModelTurn，这就是 planning。循环提供重新规划机会。

### 3. 无 Tool Call：结束

```python
if not turn.tool_calls:
    answer = turn.content.strip() or "模型未返回有效答案。"
    self.memory.append(session_id, {"role":"assistant", "content":answer})
    return AgentResult(answer=answer, steps=step, trace=trace)
```

停止条件是 tool_calls 为空。最终 user/assistant 被持久化，中间工具消息目前只在本次 run 存在。

### 4. 有 Tool Call：保存动作请求

内部 arguments 是 dict，但 Chat Completions message 需要 JSON 字符串，所以构造 `assistant_tool_message` 时再次 `json.dumps()`。

### 5. 执行并观察

```python
for call in turn.tool_calls:
    result = self.registry.execute(call.name, call.arguments)
    trace.append({...})
    messages.append(tool_result_message(call.call_id, result))
```

一轮可返回多个调用。逐个执行并追加 Observation，然后回到模型。`steps` 是模型轮数，不等于工具次数。

### 6. 达到上限

超过 `max_steps` 返回保护性答案。这保证终止，不保证成功。

### 双工具时序

```text
step 1: LLM → search_knowledge → 检索 Observation
step 2: LLM → add_todo → SQLite Observation
step 3: LLM → 最终 content，tool_calls=[] → return
```

### 概念一一映射

- ReAct：Action → Observation → 再决策结构在 `run()`，但不输出显式 Thought；
- Planning：每轮模型动态选择下一步，不是预生成完整计划；
- State：局部 `messages/trace/step` 加持久 `MemoryStore`；
- Workflow：外层循环和停止规则确定，工具路径由模型动态决定；
- Prompt：约束策略，但不能替代校验和最大步数。

# Day 6：可靠 Agent——Prompt、错误、Trace 与循环保护

## 今天在主链的位置

仍在 `Agent.run()`，但关注正常路径之外：模型为什么少重复调用、失败怎样回传、怎样调查一次任务。

## 理论 ↔ 代码

| 概念 | 项目位置 | 不能混淆 |
|---|---|---|
| System Prompt | `prompts.py::SYSTEM_PROMPT` | 行为指导，不是安全边界 |
| Tool Error Observation | `ToolRegistry.execute()` 的 `{ok:false}` | 可恢复业务结果，不是网络异常 |
| Transport Error | `LLMRequestError` | 当前会终止本次 run，由 API 转 502 |
| Loop Guard | `Agent.max_steps` | 保证停止，不保证完成 |
| Trace | `Agent.run()` 的 trace + `_write_trace()` | 可观测记录，不等于 Memory |

## 文件级：`prompts.py`

为什么需要：把全局行为约束集中管理，避免散落在入口和工具中。删除后 Agent 仍能运行，但模型更容易猜测外部事实、丢 citation、重复搜索或声称未执行的操作。

Prompt 的规则与代码机制要成对理解：

- “必须调用工具”是软约束；真正能执行什么由 Registry 白名单硬约束；
- “保留 citation”依赖 RAG 工具真的返回 citation；
- “不要重复检索”降低无效循环，但 `max_steps` 才是最终保护；
- “不得虚构成功”与工具的 `{ok:false}` 结构配合。

## 三条失败路径

### 工具名不存在

```text
LLM → ToolCall("unknown")
Registry.get() → None
result={ok:false,error:"未知工具"}
→ role=tool → LLM 可改正或解释
```

### 参数不合法

Schema Validator 在 handler 前阻断，所以无数据库/文件副作用。细节列表进入 `details`，模型可以修正参数。

### LLM 网络或协议失败

`_post()` 重试后仍失败会抛异常。CLI 当前让异常显示，API 捕获后返回 502。它不会伪装成工具 Observation，因为失败发生在产生 ModelTurn 之前。

## Trace 的产生与去向

工具步骤记录：step、type、model_ms、model、usage、tool_ms、tool、arguments、result。最终回答步骤记录模型耗时和 usage。

```python
record = {"session_id": session_id, "input": user_input,
          "trace": trace, "answer": answer}
with self.log_path.open("a", encoding="utf-8") as handle:
    handle.write(json.dumps(record, ensure_ascii=False) + "\n")
```

JSONL 一行代表一次 `run()`，便于追加和逐条分析。日志包含参数/结果，生产系统需脱敏；当前项目没有完整 PII/secret scrubber，这是明确局限。

## 关键区别

```text
messages：给模型看的本次运行上下文，生命周期到 run() 结束
memory：跨 run 保存的 user/assistant 历史
trace：给开发者看的执行证据和指标
logs/agent.jsonl：trace 的持久化文件
```

# Day 7：Memory——不是“把聊天记录全塞进去”

## 今天在主链的位置

在每次 `Agent.run()` 开头读取历史，在接收 user 和产生最终 assistant 时写入历史。

## 对应代码

- 文件：`memory.py`
- 类：`MemoryStore`
- 函数：`__init__()`、`_connect()`、`append()`、`recent()`、`count()`、`clear()`
- 调用点：`Agent.run()`；API 的 `DELETE /memory/{session_id}`
- 测试：`tests/test_memory.py`

## 文件级拆解

它属于持久状态层。SQLite 保存跨请求的对话，`session_id` 隔离不同会话，窗口和字符预算限制发给模型的历史。

删除影响：单次 Agent 工具循环仍可工作，但下一次 `run()` 不知道此前对话，清空 Memory API 也失效。

## 类/函数级结构

```text
MemoryStore
├── __init__()     创建 messages 表，保存 window_size/max_chars
├── _connect()     事务 + 显式 close
├── append()       message dict → JSON 字符串 → INSERT
├── recent()       SELECT → dict 列表 → 窗口/字符预算
├── count()        统计某 session
└── clear()        删除某 session
```

## 数据表和数据变化

```sql
messages(id INTEGER, session_id TEXT, payload TEXT)
```

```text
{"role":"user","content":"你好"}  # Python dict
→ json.dumps(..., ensure_ascii=False)
→ payload TEXT
→ SELECT 后 json.loads()
→ 再成为 messages 中的 dict
```

## 关键代码：`recent()`

```python
rows = conn.execute(
  "SELECT payload ... WHERE session_id=? ORDER BY id DESC LIMIT ?",
  (session_id, self.window_size)
).fetchall()
messages = [json.loads(row[0]) for row in reversed(rows)]
```

数据库倒序拿“最新 N 条”更高效，随后 reversed 恢复时间正序，否则模型会先看到最新回答再看到旧问题。

字符预算从最新消息向前保留：

```python
for message in reversed(messages):
    size = len(json.dumps(message, ensure_ascii=False))
    if selected and used + size > self.max_chars:
        break
    selected.append(message)
return list(reversed(selected))
```

这里用字符数近似 token，不是精确 token budget。`if selected` 保证至少保留最新一条，即使它本身超预算。这是简单可解释的策略，也是一项可改进点。

## Memory 在 Agent 中准确如何使用

```python
messages = [system, *self.memory.recent(session_id)]
...
self.memory.append(session_id, user_message)
...
self.memory.append(session_id, assistant_message)
```

当前只持久化 user 与最终 assistant，不持久化 tool request/observation。优点是历史紧凑；缺点是下一次请求无法审计上一次的中间行动。Trace 保留中间行动，但不会自动喂给模型。

## 连接管理为什么这样写

`sqlite3.Connection` 自带的 `with` 主要管理事务，不保证关闭文件句柄。因此 `_connect()` 外层 `try/finally` 显式 `close()`，避免 Windows 临时 DB 无法删除。

# Day 8：RAG 入库链——文件怎样变成可检索 Chunk

## 今天在主链的位置

这是工具 `search_knowledge` 的数据准备阶段，发生在搜索之前：文档解析 → 切块 → SQLite → 重建索引。

## 完整入库调用链

```text
API upload / UI upload / scripts/ingest_documents.py
  ↓ HybridKnowledgeBase.ingest_file(path, source)
DocumentLoader.load(path) -> text: str
  ↓ ingest_text(text, source, title)
TextChunker.split(...) -> list[Chunk]
  ↓ SQLiteChunkStore.replace_source()
chunks 表
  ↓ HybridKnowledgeBase._reload()
BM25Retriever + VectorRetriever 重新构建
```

## 对应代码

- `rag.py::Chunk`
- `DocumentLoader.load()`
- `TextChunker.split()`
- `SQLiteChunkStore.replace_source()/all()`
- `HybridKnowledgeBase.ingest_file()/ingest_text()/_reload()`

## 文件级：`rag.py`

它同时包含 RAG 数据层与检索层。这样便于小项目学习，但生产系统可拆成 parser/chunker/store/index/retriever。删除后知识工具、文档 API 和相关评测全部失效，Todo/File 工具仍可用。

## `Chunk` 数据契约

```python
Chunk(chunk_id, source, text, position, title="")
```

- `chunk_id`：数据库主键与融合去重键；
- `source`：原文档身份；
- `text`：实际检索内容；
- `position`：生成 `[source#chunk-N]`；
- `title`：预留标题元信息。

## `DocumentLoader.load()`

输入 `Path`，先 resolve 并校验后缀；输出统一纯文本 str：

- TXT/MD：UTF-8 读取；
- PDF：`PdfReader.pages[*].extract_text()`；
- DOCX：连接 `document.paragraphs`；
- 其他后缀：ValueError。

它没有 OCR，所以扫描图片 PDF 可能得到空文本；这应作为实现边界说明。

## `TextChunker.split()` 逐步拆解

1. 统一换行并去掉首尾空白；
2. 按空行分段，优先保持自然段语义；
3. 超长段按 `step = chunk_size - overlap` 滑窗预切；
4. 尽量把短段合并到 `chunk_size`；
5. 新块继承上一块尾部 overlap；
6. source 清洗后生成稳定 `chunk_id`；
7. 返回 `list[Chunk]`。

Overlap 的作用是减少答案恰好跨边界时的信息断裂，代价是存储、索引和重复召回增加。这里的 chunk_size 是字符数，不是 token。

## `replace_source()` 为什么先 DELETE 再 INSERT

同一 source 重新入库代表更新，不应累积旧版本。事务内先删除再批量插入，可避免重复 Chunk；测试 `test_replacing_same_source_does_not_duplicate_chunks` 验证这一点。

## `_reload()` 的真实代价

```python
self.chunks = self.store.all()
self.bm25 = BM25Retriever(self.chunks)
self.vector = FastEmbedRetriever(...)  # 或 LocalVectorRetriever
```

每次入库都会读取全部 chunks 并重算整个向量矩阵。小规模项目简单可靠；大规模应使用增量索引或向量数据库。

## 阅读任务与提问

1. 用一段超过 500 字文本手画 pieces 与 merged；
2. 找到空文档在哪一步被拒绝；
3. 解释同名 source 更新为何不会重复；
4. 输入 PDF 前后数据类型怎样变化？
5. 为什么不能简单按固定 500 字无 overlap 切？

面试：“RAG 文档如何入库？”回答必须从入口一路说到索引重建，指出支持格式、段落优先、overlap、SQLite 元数据、更新语义，以及 OCR/全量重建局限。

# Day 9：RAG 检索链——BM25、向量与加权 RRF

## 今天在主链的位置

用户问题已被模型变成 `search_knowledge` ToolCall；今天看 handler `knowledge.search()` 内部怎样返回带 citation 的 matches。

## 完整检索调用链

```text
ToolRegistry.execute("search_knowledge", arguments)
  ↓ handler = HybridKnowledgeBase.search
search(query, top_k, mode)
  ├── bm25.search()
  ├── vector.search()
  └── _hybrid_search() → weighted RRF
  ↓ list[(Chunk, score)]
asdict(chunk) + score + citation
  ↓
{"query":..., "matches":[...], "retrieval":..., "total_chunks":...}
```

## BM25 对应代码

- `tokenize()`：中文按字、英文数字按词；
- `BM25Retriever.__init__()`：缓存每个文档 token、平均长度、document frequency；
- `search()`：query tokens → 每个 Chunk 的 TF/IDF 与长度归一 → 排序。

输入是 query str 和 top_k int，输出是 `list[tuple[Chunk, float]]`。它擅长专有名词、精确关键词，可解释；不擅长完全不同措辞的语义相似。

## 两种 Vector backend

### `LocalVectorRetriever`

字符 2～4 gram TF-IDF，`fit_transform(chunks)` 得到稀疏矩阵；查询用同一 vectorizer transform，再算 cosine similarity。它是真向量检索，但不是神经语义模型。

### `FastEmbedRetriever`

FastEmbed 加载 `BAAI/bge-small-zh-v1.5`，chunk/query 经模型变为 512 维向量，再计算 cosine similarity。类变量 `_models` 缓存模型实例，避免重复加载。

两者对外接口相同，因此 `HybridKnowledgeBase` 可按 `vector_backend` 替换实现。

## Hybrid 与 RRF

BM25 分数和余弦分数不在同一量纲，不能直接相加。`_hybrid_search()` 只使用排名：

```python
ranked_sources = (
  (1.4, self.bm25.search(query, fetch_k)),
  (1.0, self.vector.search(query, fetch_k)),
)
score += weight / (60 + rank)
```

- `fetch_k` 先扩大候选集；
- `chunk_id` 作为两路结果的融合键；
- BM25 权重 1.4 是基于当前固定评测调出的选择；
- 常数 60 减弱头部名次差距；
- 最后按融合分数取 top_k。

这不是“语义一定优于关键词”。当前 20 条术语型数据中，BM25 很强；神经 Vector MRR 反而较低。工程选择应由评测而非宣传决定。

## `search()` 的防御与输出

- query 去空并拒绝空值；
- top_k 限制到 1～10；
- mode 只允许三种；
- 检索器输出统一 tuple；
- `asdict(chunk)` 转 dict；
- citation 在应用侧确定性生成，不依赖模型编造。

## 阅读任务与提问

1. 解释 `fetch_k` 为什么比 top_k 大；
2. 两路都召回同一 chunk 时分数如何累加？
3. 为什么融合排名而不是原始分数？

# Day 10：RAG 如何真正参与 Agent，而不是孤立搜索模块

## 今天在主链的位置

把 Day 4、8、9 接回 Day 5：用户并不直接调用 RAG，模型先选择 `search_knowledge`，应用执行，结果再回模型生成带来源回答。

## 跨文件调用链

```text
Agent.run()
  ↓ registry.schemas()
create_registry() 注册的 search_knowledge Schema
  ↓ LLM 选择
ToolCall(name="search_knowledge", arguments={query, top_k, mode})
  ↓ Agent.run()
ToolRegistry.execute()
  ↓ Tool.handler
HybridKnowledgeBase.search()
  ↓ BM25 / Vector / RRF
matches + citation
  ↓ tool_result_message()
role=tool Observation
  ↓ OpenAICompatibleClient.complete()
LLM 根据检索证据组织最终 answer，并按 Prompt 保留 citation
```

## 关键绑定发生在哪里

```python
registry.register(Tool(
    name="search_knowledge",
    ...,
    handler=knowledge.search,
))
```

`handler=knowledge.search` 是绑定方法：它已经绑定具体 `knowledge` 实例。Registry 执行时只需 `handler(**arguments)`，无需知道 BM25、向量模型或数据库。

## 谁负责 citation 的哪一部分

1. `HybridKnowledgeBase.search()` 确定 source/position 并生成 citation；
2. `ToolRegistry` 不修改数据，只包装 ok/data；
3. `tool_result_message()` 将其序列化给模型；
4. SYSTEM_PROMPT 要求模型在相关表述后保留 citation；
5. 当前系统没有最终答案 citation validator，所以模型仍可能遗漏，这是局限。

## RAG 与 Memory 的区别

```text
RAG：从文档库按当前 query 检索，结果通过工具进入本轮 messages
Memory：按 session 取最近对话，在 run 开头直接进入 messages
```

RAG 解决外部知识，Memory 解决对话连续性；二者数据来源、检索方式和生命周期不同。

## 一次请求的状态快照

```python
messages = [system, history..., current_user]

# RAG 执行后
messages += [{"role":"tool", "tool_call_id":..., "content":"{matches...}"}]

# 再请求模型后
answer = turn.content
```

# Day 11：FastAPI、Streamlit 与文件安全——入口层不应复制业务逻辑

## 今天在主链的位置

今天在主链最前端：HTTP/UI 输入如何变成 `Agent.run()` 或 `knowledge.ingest_*()` 调用，以及结果如何返回客户端。

## 对应代码

- FastAPI：`api_main.py`、`api.py::create_api()`；
- 请求/响应契约：`ChatRequest`、`ChatResponse`、`TextDocumentRequest`；
- UI：`ui.py::get_components()` 与 chat/upload 分支；
- 文件工具：`tools.py::FileFinder`；
- 共用组装：`app.py::build_components()`。

## 文件级：`api_main.py` 与 `api.py`

`api_main.py` 只负责启动 Uvicorn。真正的 API 工厂是 `create_api()`。删除 `api_main.py` 后仍可用其他 ASGI 命令启动 `workbench_agent.api:app`；删除 `api.py` 才会失去 HTTP 接口。

```text
api_main.py → uvicorn → api.py:app
api.py route → get_components() → AppComponents
                         ├→ agent.run()
                         ├→ knowledge.ingest_*()/stats()
                         └→ memory.count()/clear()
```

### 为什么 `components` 延迟创建

```python
components: AppComponents | None = None
def get_components():
    nonlocal components
    if components is None:
        components = build_components(data_dir, online=online)
    return components
```

第一次请求才加载 BGE/数据库，后续请求复用同一实例。`nonlocal` 表示修改外层 `create_api()` 的局部变量。测试可调用 `create_api(tmp_path, online=False)`，得到隔离数据库和离线模型。

## `/chat` 的数据变化

```text
HTTP JSON {message, session_id}
→ Pydantic ChatRequest（长度校验）
→ agent.run(str, str)
→ AgentResult
→ ChatResponse(answer, steps, trace)
→ HTTP JSON
```

业务异常映射：LLM 网络/协议错误 → 502；用户输入等 ValueError → 400。Tool handler 异常通常已经成为 Observation，不会走这里。

## 上传文件的安全边界

`upload_document()` 做了四层控制：

1. 后缀必须在 loader 支持集合；
2. 读取后限制 10 MB；
3. 使用临时目录；
4. `Path(filename).name` 去掉客户端传来的目录部分，降低路径穿越风险。

之后才调用 `knowledge.ingest_file()`。当前只按后缀而非 MIME/魔数判断，压缩炸弹、恶意解析文件和并发资源控制仍是生产化改进点。

## 文件级：`ui.py`

UI 负责输入、显示和页面状态：

```python
result = service.agent.run(prompt, session_id=session_id)
st.markdown(result.answer)
st.json(result.trace)
```

它没有复制 Agent Loop。`st.session_state.messages` 只用于页面展示；真正给模型的跨请求历史由 `MemoryStore` 管理。`@st.cache_resource` 复用重型服务对象。

## `FileFinder` 与文档上传不是一回事

`FileFinder.find()` 只在固定 `workspace` 根目录中按文件名搜索，返回相对路径和大小；它不会读文件内容。`root.resolve()` 在初始化时确定，模型参数中没有 path，因此模型不能请求搜索任意系统目录。

## 关键测试：`ScriptedModel`

```python
class ScriptedModel:
    def complete(self, messages, tools):
        self.calls += 1
        if self.calls == 1:
            return ModelTurn(tool_calls=[ToolCall("echo", {"text":"hello"}, "call-1")])
        assert messages[-1]["role"] == "tool"
        return ModelTurn(content="已根据工具结果完成任务")
```

它不是在模拟语言智能，而是在精确控制协议：第一轮请求工具，第二轮确认 Agent 已追加 Observation 后给答案。因此测试失败时更容易定位为主循环问题，而非模型随机性。

测试中的 `echo` 工具也是局部注册：

```text
ToolCall("echo")
→ Registry 找到 lambda handler
→ {echo:"hello"}
→ role=tool
→ ScriptedModel 第二轮
→ AgentResult
```

## `LoopingModel` 为什么重要

它每轮都请求不存在的工具。Registry 每次返回错误 Observation，但模型仍继续请求。`max_steps=2` 后 Agent 必须停止。这验证“失败不会崩溃”和“失败也不会无限运行”两个不同性质。

## `FakeClient` 的继承点

它复用 `OpenAICompatibleClient.complete()`，只覆盖 `_post()`。这是 seam（可替换接缝）：网络是慢且不稳定的外部边界，payload 构造和解析是应确定验证的本地逻辑。

## API 测试是真集成还是单元测试

`TestClient(create_api(tmp_path, online=False))` 同时经过路由、组装、Agent、工具和临时 SQLite，属于轻量集成测试。它没有真实网络模型，因此仍可重复。

## 项目真实 Debug 案例：SQLite 文件句柄

症状：指标全部打印，但 Windows 清理临时目录报 WinError 32，退出码 1。

定位：数据库功能正常，失败发生在进程收尾；临时 DB 仍被占用。Python 的 `with sqlite3.connect(...)` 管理 commit/rollback，但连接句柄没有及时关闭。

修复：`MemoryStore`、`TodoStore`、`SQLiteChunkStore` 的 `_connect()` 使用 contextmanager，在 finally 中 `conn.close()`。结果：17 项测试通过，六组检索指标不变，评测退出码恢复 0。

这类案例在面试中比“我修了一个 bug”更有价值：能讲症状、分层定位、根因、修改范围和回归证据。

## 另一个案例：Embedding 依赖选择

原方案 `sentence-transformers` 会引入较重 PyTorch 依赖；改用 FastEmbed + ONNX，在 CPU 上运行 BGE，同时保留 TF-IDF 基线。这里体现的不是“某库最好”，而是根据交付环境、模型质量和依赖体积做权衡。

## 今天在主链的位置

## 功能修改定位表

| 需求 | 主要修改位置 | 通常不该修改 | 必须补的验证 |
|---|---|---|---|
| 新增一个工具 | `tools.py::create_registry()`，必要时新增 Store/Service | `Agent.run()` | Schema 类型、成功、错误、Agent 调用 |
| 更换模型服务 | 新 `ModelClient` adapter 或 `llm_client.py` | Tool/RAG | payload、响应解析、错误映射 |
| 改 Agent 停止策略 | `agent.py::run()` | 各 handler | 循环/重复调用/最终回答测试 |
| 精确 token Memory | `memory.py::recent()` | UI session state | 预算、顺序、session 隔离 |
| 新文档格式 | `DocumentLoader` | Agent Loop | 解析、空文档、异常文件 |
| 换向量数据库 | `rag.py` 的 Store/Retriever 边界 | CLI/API 路由 | 持久化、top-k、更新语义 |
| 强制 citation | `Agent` 最终答案校验 + Prompt | BM25 公式 | 有/无证据回答测试 |
| 新 HTTP endpoint | `api.py` | 核心业务重复实现 | 状态码、request/response |
| 页面新展示 | `ui.py` | Agent 逻辑 | 手工/UI 测试 |

## 示例一：新增 `delete_todo`

推荐步骤：

```text
TodoStore.delete(todo_id)             # 领域操作
→ create_registry() 注册 Tool          # Schema + handler
→ test_tools.py                        # 存在/不存在/类型错误
→ agent case                           # 模型是否能选择它
```

无需在 Agent 写：

```python
if call.name == "delete_todo": ...  # 不推荐
```

因为 Registry 已经承担分发。若每个新工具都改 Agent，主循环会随工具数量膨胀。

## 示例二：加入重复调用去重

应主要改 `Agent.run()`，因为它掌握跨 step 的调用历史：

1. 将 `(call.name, canonical_json(arguments))` 作为 signature；
2. 在本次 run 的 set 中记录；
3. 再次出现时生成结构化错误 Observation 或触发停止；
4. Trace 标明 duplicate；
5. 测试模型连续返回同调用时的行为。

不要把去重写进某一个 handler，否则只能保护一个工具，也看不到跨工具编排状态。

## 示例三：真正的长期 Memory

不能只把 `window_size` 调大。合理拆分：

- 短期对话：当前 `MemoryStore`；
- 长期事实/偏好：独立结构化记录或向量库；
- 写入策略：哪些内容值得记；
- 读取策略：按当前任务检索哪些记忆；
- 更新/遗忘：冲突事实怎样覆盖；
- 隐私：用户如何查看和删除。

这说明 “Memory” 是策略与生命周期，不只是数据库表。

## 代码设计思想总结

- Dependency Injection：`app.py` 创建，Agent 接收；
- Interface/Adapter：`ModelClient` 与真实客户端；
- Registry：动态工具分发；
- DTO/Data Contract：`ToolCall/ModelTurn/AgentResult/Chunk`；
- Separation of Concerns：入口、编排、工具、存储、模型适配分层；
- Fail as Data：工具异常转 Observation；
- Defense in Depth：Prompt 软约束 + Schema/白名单/步数硬约束。

## 实际阅读任务

不改代码，分别为以下需求写“修改计划＋测试计划”：

1. 新增删除待办；
2. 对重复 Tool Call 去重；
3. 支持 `.html` 文档；
4. citation 缺失时自动重试一次；
5. Memory 从字符预算改精确 token 预算。

每个计划必须指出文件、类、函数、输入输出变化和可能破坏的调用者。

面试：“如果让你新增一个工具怎么改？”不能只答“在 tools.py 加函数”；要讲领域 handler、Schema、Registry 注册、Agent 无需改变、错误 Observation 和多层测试。

| Tool Calling | 模型请求、应用执行 | ToolCall → Registry.execute → tool message |
| Memory | 跨请求历史策略 | `MemoryStore.recent()/append()` |
| RAG | 外部文档检索增强生成 | `HybridKnowledgeBase` + search tool |
| Embedding | 文本到向量 | `FastEmbedRetriever` / `LocalVectorRetriever` |
| Observability | 记录执行证据 | trace 列表 + `_write_trace()` |
| Evaluation | 固定输入和标准衡量行为 | `scripts/evaluate_*.py` |

# 附录 C：常见误解纠正

1. 项目没有 `think()`、`Planner`、`ToolExecutor` 独立类；对应行为在 `model.complete()` 与 `ToolRegistry.execute()`。
2. 模型不执行 Python 函数；它只返回结构化调用请求。
3. Tool Schema 不等于绝对安全；应用仍需白名单、校验和权限边界。
4. Memory 不等于 Streamlit 页面聊天记录，也不等于 Trace。
5. RAG 不是把整个文档塞进 Prompt，而是检索 Top-K Chunk。
6. Vector 不必然是神经 Embedding；项目同时有 TF-IDF baseline 和 BGE。
7. 17 项测试通过不代表真实模型答案永远正确；因此另有在线评测。
8. Prompt 不能代替代码中的 max_steps、Schema 和路径限制。
