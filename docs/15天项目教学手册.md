# Day 1：系统全貌与一次请求

## 目标与知识位置

能不看代码画出：

```text
用户 → Agent → LLM → Tool → Observation → LLM → 最终回答
```

本项目属于 LLM 应用开发：Agent 是主线，RAG 是 Agent 的一个工具，Memory 保存状态，API/UI 提供入口，Evaluation 判断是否真的工作。

## 核心代码

按顺序阅读：

1. `main.py`：CLI 入口。
2. `src/workbench_agent/app.py`：组件组装。
3. `src/workbench_agent/agent.py`：执行循环。
4. `src/workbench_agent/tools.py`：工具。
5. `src/workbench_agent/rag.py`：知识检索。

`app.py::build_components()` 连接模型、知识库、工具、Memory 和 Agent。它是装配层，不负责具体检索或业务算法。

## 真实数据流

问题“查 Tool Calling 的定义，并记录复习待办”会经过：

1. `main.py` 调用 `agent.run()`。
2. Agent 读取当前 session 历史。
3. messages 和 5 个 Tool Schema 发给 LLM。
4. LLM 返回 `search_knowledge`。
5. Python 检索并回传 `role=tool`。
6. LLM 返回 `add_todo`。
7. Python 写 SQLite 并回传。
8. LLM 输出最终回答。
9. Agent 保存 Memory 和 Trace。

## 验证

```powershell
python main.py --online
Get-Content logs\agent.jsonl -Tail 1 -Encoding utf8
```

输入：“根据知识库解释 Tool Calling，并新增待办：复习 Tool Calling。”观察 Trace 中的工具顺序、参数、结果和耗时。

## 面试题

**为什么不是普通 ChatBot？** 普通 ChatBot 通常只返回文本；本项目需要读取私有知识、搜索文件和修改待办，必须由受控工具完成。

**为什么是单 Agent？** 任务共享一个目标和工具集，不需要角色隔离；Multi-Agent 会增加状态同步、延时和评测难度。

- [ ] 能画出 9 步请求流程。
- [ ] 能说出 `app/agent/tools/rag` 的职责。
- [ ] 能解释为什么模型不能直接修改 SQLite。

# Day 2：LLM API、messages 与模型适配器

## 目标与代码

阅读 `contracts.py`、`config.py`、`llm_client.py`、`prompts.py`，理解四种消息角色和适配器。

LLM API 通常无状态。多轮对话是应用每次重新发送需要的历史：

```json
[
  {"role":"system","content":"全局规则"},
  {"role":"user","content":"查知识库"},
  {"role":"assistant","tool_calls":[]},
  {"role":"tool","tool_call_id":"call_1","content":"检索结果"}
]
```

- `system`：全局行为规则。
- `user`：用户目标。
- `assistant`：模型文本或工具请求。
- `tool`：应用执行工具后的真实结果。

## Protocol 与适配器

`ModelClient` 只规定 `complete(messages, tools) -> ModelTurn`。Agent 不依赖学校 API 的原始 JSON。测试可换 `ScriptedModel`，以后可换其他服务。

`llm_client.py` 把 `function.arguments` 的 JSON 字符串执行 `json.loads()`，转换成项目内部 `ToolCall`。非法 JSON 抛 `LLMProtocolError`，不能直接进入 handler。

## 重试

网络瞬时错误、429、5xx 使用指数退避；400 参数错误和 401/403 鉴权失败不盲目重试。

## 验证

```powershell
python scripts\probe_school_api.py
python -m pytest tests\test_llm_client.py -v
```

## 面试题

**LLM API 有状态吗？** 通常没有，应用通过 messages 模拟多轮，SQLite 负责保存需要的历史。

**为什么不在 Agent 中解析 HTTP JSON？** 会与供应商格式耦合；适配器把外部格式转换成统一 `ModelTurn`。

**为什么 401 不重试，429 要重试？** 401 通常是凭据错误，重复无效；429 是短期限流，退避后可能恢复。

## 验收

- [ ] 能解释四种 role。
- [ ] 能解释 `ModelTurn` 与 API JSON 的关系。
- [ ] 能区分可重试与不可重试错误。

# Day 3：Tool、JSON Schema 与 Registry

## 目标与代码

阅读 `tools.py` 中的 `Tool`、`Tool.schema()`、`ToolRegistry`、`create_registry()`。

```python
Tool(
    name="add_todo",
    description="新增一条待办事项。",
    parameters={...},
    handler=todos.add,
)
```

`name/description/parameters` 给模型，`handler` 只给 Python 应用。模型只能生成工具名和参数，真正执行的是 `tool.handler(**arguments)`。

JSON Schema 约束类型、必填、范围、枚举和额外字段。项目用 `Draft202012Validator`，不是只检查字段存在。

Registry 避免 Agent 写大量 if/elif。新增 Tool 不修改主循环，未知名称也不会执行任意函数。

## 验证

```powershell
python -m pytest tests\test_tools.py -v
```

重点观察整数参数传成字符串时返回“工具参数校验失败”。

## 面试题

**Tool Schema 给谁用？** 模型用它生成结构化参数，应用用它校验；handler 由应用执行。

**模型返回未知工具怎么办？** Registry 返回失败 Observation，不动态导入或执行任意代码。

**description 写不好会怎样？** 模型可能选错工具或参数，因此描述也属于可靠性和评测范围。

## 验收

- [ ] 能区分 Schema 与 handler。
- [ ] 能解释 `additionalProperties=False`。
- [ ] 能解释 Registry 的扩展价值。

# Day 4：Agent 主循环与多步任务

## 目标与代码

逐段阅读 `agent.py::Agent.run()`。

```python
messages = [system_prompt, *memory.recent(session_id)]
for step in range(1, max_steps + 1):
    turn = model.complete(messages, registry.schemas())
```

没有 Tool Call 时返回最终文本；有 Tool Call 时必须先追加 assistant 的工具请求，再执行工具并追加同 `call_id` 的 `role=tool` 结果。

真实案例：第 1 轮模型选择检索，第 2 轮选择待办，第 3 轮输出文本，因此 `steps=3`、`tools=2`。

`max_steps=6` 是死循环、延时和 Token 成本的硬边界。

## 验证

```powershell
python -m pytest tests\test_agent.py -v
```

## 面试题

**Agent 和 Workflow 的区别？** Workflow 主要步骤预先定义；Agent 根据目标和 Observation 动态选择。可固定的文档入库仍使用 Workflow。

**为什么调用工具后还请求模型？** 工具只返回数据，模型需要读取 Observation，判断是否继续并组织回答。

**为什么保留 assistant tool_calls？** 协议需要 `tool_call_id` 把工具结果和原请求关联。

## 验收

- [ ] 能逐段复述 `Agent.run()`。

## 目标

```json

  "type": "tool_call",
  "model_ms": 820.4,
  "tool_ms": 3.1,
  "tool": "search_knowledge",
```

# Day 6：RAG 全流程、文档解析与 Chunk

## 目标与流程

```text
文档解析 → 清洗 → Chunk → Embedding → Vector Store
→ Query Embedding → Top-K → Context → Generation → Citation
```

RAG 不等于上传文件或向量数据库，完整链路至少包含检索和生成。

## 核心代码

阅读 `rag.py` 的 `Chunk`、`DocumentLoader`、`TextChunker`、`SQLiteChunkStore`。

- TXT/Markdown：UTF-8 文本。
- PDF：pypdf；扫描 PDF 需要 OCR，当前不支持。
- DOCX：python-docx 段落。

Chunk 参数是 500 字符、80 字符重叠。优先按段落，超长段使用字符滑窗。元数据包括 `chunk_id/source/title/position/text`，引用由 source 和 position 生成。

太小会语义断裂和增加索引；太大会增加噪声、Token 和定位难度。Overlap 太小丢边界，太大产生重复。

## 验证

```powershell
python scripts\ingest_documents.py knowledge
python -m pytest tests\test_rag.py -v
```

## 面试题

**为什么不把整篇文档直接给模型？** 上下文有限、成本和噪声高，也难以稳定引用。

**相同 source 为什么覆盖？** 避免更新后残留旧 Chunk 和重复结果。

**如何处理表格、图片、扫描 PDF？** 当前不覆盖；需要版面解析、OCR 或多模态模型。

## 验收

- [ ] 能画完整 RAG 流程。
- [ ] 能解释 500/80 的取舍。

# Day 7：Embedding、向量检索与余弦相似度

## 目标

理解项目用了什么 Embedding，向量如何比较，以及哪些能力来自预训练模型。

项目使用 `BAAI/bge-small-zh-v1.5`，输出 512 维向量，通过 FastEmbed + ONNX 在 CPU 推理。项目没有训练 BGE，只负责加载、生成向量、索引和评测。

阅读 `rag.py::LocalVectorRetriever` 和 `FastEmbedRetriever`：

```python
matrix = np.vstack(list(model.embed(chunk_texts)))
query_vector = np.vstack(list(model.embed([query])))
scores = cosine_similarity(query_vector, matrix)[0]
```

余弦相似度比较向量方向：`cos(q,d)=(q·d)/(||q||||d||)`。分数高表示向量接近，不保证答案正确。

两种后端：`tfidf` 是字符 n-gram 基线；`fastembed` 是 BGE 神经 Embedding。

当前 Chunk 在 SQLite，向量矩阵在进程内，是本地 Vector Store，不是独立 Vector Database。新增文档会重建矩阵。

## 验证

```powershell
python scripts\evaluate_retrieval.py
```

观察 BGE Vector 并不一定优于 TF-IDF，这是评测结论，不应隐瞒。

## 面试题

**Embedding 如何训练？** 通常通过对比学习让相关文本靠近；本项目没有训练，使用预训练 BGE。

**为什么不需要 GPU？** BGE-small 使用 ONNX CPU 推理，个人知识库规模足够。

**用了向量数据库吗？** 没有；是进程内矩阵加 SQLite 元数据，大规模再迁移 Qdrant/Milvus/pgvector。

## 验收

- [ ] 能解释 512 维和余弦相似度。
- [ ] 能区分 TF-IDF 与 BGE。
- [ ] 不把模型权重说成自己训练。

# Day 8：BM25、Hybrid Search 与检索评测

## 目标

理解为什么 Embedding 不会自动优于关键词检索，以及项目如何用数据选择融合策略。

BM25 综合词频 TF、逆文档频率 IDF 和文档长度归一化，对专有名词、代码标识和精确关键词很强。

项目不直接相加 BM25 与余弦分数，因为量纲不同，而用 RRF：

```text
score += weight / (60 + rank)
BM25 weight=1.4，Vector weight=1.0
```

等权 BGE Hybrid 曾在 20 条评测上漏掉“如何避免智能体无限循环”，Hit@3=0.95。提高 BM25 权重后 Hit@3=1.0。权重只对当前小数据负责。

- Hit@3：正确来源是否在前三。
- MRR@3：正确来源第 1 名得 1，第 2 名得 1/2，第 3 名得 1/3。

实际 MRR@3：BM25 0.9167，BGE Vector 0.8750，Weighted Hybrid 0.9417。

## 验证

阅读 `evals/retrieval_cases.json`、`scripts/evaluate_retrieval.py`，再运行评测。

## 面试题

**Top-K 为什么不是越大越好？** 过大增加噪声、Token 和延时；过小漏证据，需要综合检索与生成指标。

**BGE 为什么没单独取得最高 MRR？** 数据小且术语重合明显，词法基线很强；需更多同义改写和困难负样本。

**20 条评测证明什么？** 只作为当前场景回归集，不能代表开放领域准确率。

## 验收

- [ ] 能解释 Hit@K、MRR 和 RRF。
- [ ] 能说明 1.4/1.0 的实验来源。
- [ ] 能诚实说明评测局限。

# Day 9：Memory、SQLite 与上下文预算

## 目标

区分“保存消息”“Memory 策略”和“长期记忆”。阅读 `memory.py` 与 `tools.py::TodoStore`。

当前策略：SQLite 持久化、session_id 隔离、最近 12 条、最多 12000 字符。`recent()` 按 session 查询，再从最新消息向前累加预算。

不能发送全部历史，因为上下文有限、成本和延时增加、无关信息干扰且可能泄露隐私。

SQLite 是存储层；窗口、预算、摘要和相关记忆检索才是策略。当前没有跨会话用户画像、自动摘要或长期记忆检索。

## 验证

```powershell
python -m pytest tests\test_memory.py -v
```

## 面试题

**为什么同时限制条数和字符？** 条数不能反映消息长度，字符预算提供第二道上限；生产可用 tokenizer 精确计算。

**多用户如何防串线？** 当前用 session_id；真实系统还要绑定鉴权 user_id，不能信任客户端任意传入。

**为什么不用 Redis？** 单机项目 SQLite 更低运维；多实例共享状态时再引入 Redis/PostgreSQL。

# Day 11：文件安全边界与 Streamlit UI

# Day 12：自动测试、Fake Model 与 Agent 评测

## 目标

理解“成功演示一次”不等于可靠。

三层测试：

1. pytest 用 Fake/Scripted Model，稳定覆盖 Agent、Tool、RAG、Memory、API 和协议。
2. 20 条 Retrieval Eval 只评 Hit@3/MRR@3。
3. 8 条真实 Agent Eval 检查工具、额外调用、答案、引用和效率。

真实模型不放进普通单测，因为有网络波动、非确定性和额度成本。

第一版 Agent 评测只检查“预期工具出现”，把额外 `answer` 工具和“已查”短回答误判为成功。收紧后同一版本出现过 8/8 和 7/8；最新失败项是重复检索超限。

# Day 13：Debug 方法与真实故障复盘

## 通用流程

```text
读完整错误 → 判断层级 → 最小复现 → 检查边界
→ 写回归测试 → 修复 → 单测 → 端到端 → 记录
```

## 五个真实案例

### ModuleNotFoundError

pytest 能导入但直接运行不能。原因是 src 布局的模块搜索路径不同；标准修复是可编辑安装，入口另有兜底。经验：比较成功和失败路径的环境差异。

### Windows 中文乱码

`conda run` 捕获输出与终端编码不一致。批处理启用 UTF-8。经验：先区分数据损坏和显示解码。

### SQLite 临时文件占用

结果生成但 Windows 清理报 WinError 32。允许临时目录延迟清理并验证退出码。经验：业务成功和测试夹具清理是两个维度。

### Embedding 依赖过重

sentence-transformers 拉取大体积 PyTorch，最终换 FastEmbed + ONNX。经验：选型要考虑部署体积和安装稳定性。

### 评测误判

打印 8/8 但模型幻觉 `answer` 工具。原因是断言太宽松；增加额外工具、回答、引用和效率检查。经验：测试本身也可能有 Bug。

## 面试题

**最有价值的 Debug？** 评测误判，因为它是验收标准错误，修复后暴露了真实模型非确定性。

**如何防止回归？** 把最小复现变成测试，再执行模块、全量和端到端验证。
